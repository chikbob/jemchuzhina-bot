# Данные, веб-кабинет и восстановление

## Хранение

Одна SQLite-база, путь задаётся `DATABASE_PATH`. Окна (`slots`) связаны с записями (`bookings`) внешним ключом; имя, телефон, анкета и комментарии сохраняются с каждой записью. Заявки на обучение лежат в `leads`. Роли — в `staff`, профили сотрудников — в `users`. Индексы ускоряют поиск записей по клиенту, проверку занятости окна и выбор расписания. Транзакции защищают резервирование мест и изменение статуса.

Анкеты, очереди сообщений и служебные записи отделены от клиентских данных. Web и Telegram обращаются к одной базе; отдельного дублирования данных для веб-кабинета нет.

## Веб-кабинет

Адрес: `/admin/`. Доступны обзор дня, поиск и фильтры записей, карточка с комментариями, расписание, заявки на обучение, сотрудники, CSV и резервные копии. Изменять записи и роли по-прежнему можно в Telegram. Фото отмечаются в карточке как приложенные; просмотреть их можно в Telegram.

Доступ защищён отдельным паролем веб-кабинета. Он не совпадает с паролем сотрудников Telegram. Чтобы получить данные входа локально:

```bash
.venv/bin/python scripts/manage_data.py web-access
```

Команда сохраняет адрес и пароль в `data/web-access.txt` с правами `0600`; в журнал пароль не выводится. Если `WEB_PANEL_PASSWORD` не задан, стабильный случайно выглядящий пароль вычисляется из имеющихся приватных секретов. При необходимости можно задать свой `WEB_PANEL_PASSWORD` (минимум 16 символов) через окружение и перезапустить приложение.

Страницы требуют входа, содержат запрет кеширования и заголовки защиты; cookie HttpOnly/SameSite, на хостинге Secure. Сеанс истекает после двух часов бездействия. Вход и служебные POST защищены CSRF-токеном, после пяти неверных паролей действует 15-минутная блокировка по адресу клиента. В CSV опасные формулы экранируются.

Для локальной разработки на HTTP можно установить `WEB_COOKIE_SECURE=0` только в локальном окружении. На хостинге оставляйте `1` и используйте HTTPS. Пароли, файлы БД и копии не включаются в Git или Docker-образ.

## Очистка перед запуском

```bash
.venv/bin/python scripts/manage_data.py reset --confirm RESET
```

Сначала создаётся проверенная SQLite-копия в `data/backups` с правами `0600`, затем очистка выполняется одной транзакцией под блокировкой webhook. Удаляются окна, записи, заявки, профили клиентов, незавершённые анкеты, очереди сообщений, сеансы и прочие рабочие таблицы.

Сохраняются сотрудники, их роли и профили, а также минимальные технические маркеры назначения владельца: очистка не может случайно вернуть права прежнему владельцу через `OWNER_IDS`. Одобрение записи возвращается в автоматический режим, публикация отключается до нового включения. Старые события Telegram отсеиваются по времени очистки; они не должны заново заполнить базу старыми заявками.

После очистки сотрудники открывают `/start`; владелец при необходимости входит через `/admin`. Очищается база, а не история чатов на устройствах пользователей.

## Откат очистки

```bash
.venv/bin/python scripts/manage_data.py restore \
  --backup data/backups/before-reset-ДАТА-ИДЕНТИФИКАТОР.sqlite3 \
  --confirm RESTORE
```

Восстанавливаются окна, записи, заявки и профили клиентов. Текущие сотрудники и роли сохраняются: откат данных не возвращает уже отозванный доступ. Старые уведомления и анкеты не воспроизводятся. Перед восстановлением автоматически создаётся ещё одна копия — для обратного отката.

Для полного переноса на другой сервер используйте целый снимок SQLite по [инструкции хостинга](HOSTING.md); это отдельная операция от восстановления только клиентских данных.
