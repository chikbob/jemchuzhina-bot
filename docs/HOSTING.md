## Рекомендация

Для запуска академии проще перейти на PythonAnywhere Developer: данные остаются в том же аккаунте, доступно больше web-worker и исчезает ограничение внешнего интернета. Это не обещание конкретного времени ответа: задержки Telegram и работа приложения также влияют на скорость.

Если важнее развёртывать прямо из GitHub и иметь Docker-процесс, можно выбрать Railway с постоянным диском. Следите за фактическим потреблением: Hobby не является безлимитным тарифом за фиксированные $5.

Vercel технически принимает Python/Flask, однако бесплатный Hobby предназначен для личных некоммерческих проектов. Рабочий бот академии относится к бизнесу. Файловая система функций доступна на запись только во временном `/tmp`; хранить там рабочую SQLite нельзя. Для Vercel нужна внешняя постоянная БД и замена файловой блокировки общей координацией между экземплярами. Поэтому переход туда сейчас не упрощает проект и не уменьшает базовую стоимость.

Платные тарифы или новый аккаунт этим обновлением не подключаются. Готов переносимый WSGI/Docker-вариант, чтобы выбор провайдера не связывал проект с одним сервисом.

## Перенос на сервер с постоянным диском

1. Сохраните SQLite через «Резервные копии» в веб-кабинете или `scripts/manage_data.py backup`. Это полная согласованная копия базы.
2. Подготовьте новый сервер из того же Git-коммита. Перенесите `.env` приватно; задайте новый `WEBHOOK_BASE_URL`, правильный `DATABASE_PATH` и постоянный диск.
3. Убедитесь, что старый webhook временно не обрабатывает новые записи во время финального снимка и переключения. Повторно создайте финальную копию и перенесите её целиком на новый диск, сохраняя staff, настройки и обработанные update ID.
4. Запустите web-режим; проверьте `/health`, вход в `/admin/`, роли, даты и число записей. Нужен один экземпляр SQLite на постоянном диске; файл БД не следует раздавать нескольким независимым репликам.
5. Выполните на новом сервере `scripts/configure_webhook.py`: он меняет HTTPS-адрес, не сбрасывая очередь Telegram. Остановите старое приложение, чтобы оно не конкурировало за работу.
6. Проверьте `/start` и одну запись. Сохраните старую копию для отката.

Публикация в два хостинга одновременно с разными копиями SQLite не синхронизирует данные. Для горизонтального масштабирования нужна серверная БД.

## Docker / Gunicorn

```bash
docker compose -f compose.web.yaml up -d --build
```

Образ собирается через `Dockerfile.web`. База находится в именованном томе `/app/data`; веб-сервер слушает `PORT` (по умолчанию 8080). В примере порт привязан к `127.0.0.1`: снаружи его должен обслуживать HTTPS reverse proxy. В Docker `.env` передаётся окружением и не включается в образ.

Для сервиса с Dockerfile в панели хостинга выберите `Dockerfile.web`, задайте переменные окружения, подключите постоянный диск и направьте `DATABASE_PATH` в него. У пользователя процесса должны быть права записи в каталог диска. Проверьте эти права до переноса рабочей базы.

Пакеты для обычного Linux-хостинга:

```bash
pip install -r requirements-deploy.txt
gunicorn app:app --bind 0.0.0.0:8080 --workers 1 --threads 4 --timeout 90
```
